# 项目架构

## 组件边界

- ESP32-S3 采集和播放音频，通过认证 WebSocket 将音频帧交给 Go 后端；唤醒检测和音频分流由服务端负责。
- 灵矽提供语音识别、智能体语义理解、MCP 工具调用和语音回复。
- Go 后端维护好友、配对口令、房间、邀请确认和在线状态。
- Janus Gateway AudioBridge 在服务端处理 WebRTC 实时音频和房间混音。

## 麦克风音频路由

Go 服务为每台设备维护短时音频缓冲和路由状态：设备已加入房间时，普通语音进入对应 Janus 房间；未加入房间时仍运行唤醒检测，但丢弃普通语音且不积压到 Janus 队列。检测到唤醒词后清除回看缓存及房间下行，再把后续指令音频交给该设备独立的灵矽会话。灵矽 TTS 播放期间不向扬声器发送房间混音，TTS 停止并收到设备播放排空确认后恢复房间模式。

灵矽上行使用 PCM16 16 kHz，不能据此推断下行也是 PCM。[官方 WebSocket 文档](https://linx.qiniu.com/docs/xrobot/platform/websocket) 明确 TTS 下行为 Opus（16/24 kHz、20/40/60 ms）。Go 在每条灵矽连接上独立维护 Pion Opus 解码器，直接输出 16 kHz 单声道 PCM，再拆成 ESP32 可接受的 640 字节/20 ms 帧。参数不支持或解码失败时记录格式/包长并断开重试，不把压缩数据送入 I2S。该转换已经合成音协议测试，真实平台音质与 TTS 播放收尾时序仍待联调。

TTS 二进制帧和文本状态事件在 Go 接收后共用有界有序队列；队列满时背压传回灵矽 WebSocket，避免丢弃句中音频。设备下行每发一帧间隔 20 ms，并将正常 `tts.stop` 放在音频尾帧之后；ESP32 把播放排空标记排在待播帧之后，标记处理完成后回传 `playback/drained`，Go 收到后才恢复房间模式。打断时设备先收到 `is_aborted=true` 并清队列，再收到房间模式切换。协议测试覆盖正常结束和打断顺序；I2S DMA 与 Codec 的实际声学收尾延迟仍待实体设备测量。

WebSocket hello 不声明设备侧 `mcp` 能力，因为设备侧 MCP RPC 没有在这条连接上实现。业务工具走智能体配置的独立云端 MCP 端点；官方 Go MCP SDK 处理 `initialize`、初始化通知、工具发现、调用和 SSE 响应。标准 MCP 客户端测试已覆盖两台设备的握手、工具调用、身份隔离及断线清理，真实灵矽平台接入仍待账户联调。

当前唤醒短语为“灵矽灵矽”。代码包含可替换的 `WakeWordDetector` 接口，并在 Linux amd64/arm64 + CGO 部署中接入 sherpa-onnx 开放词汇 KWS；`deploy/prepare-kws.sh` 下载并校验中文 Zipformer int8 模型文件，再生成匹配模型词表的关键词文件，无需训练。模型权重留在 Git 忽略目录，部署时需单独运行准备脚本。每台在线设备独立加载模型和流状态，服务端内存随在线设备数增长。回看窗口当前按 50 个 20 ms 帧估算为约 1 秒，目标短语的录音评测前不能保证唤醒词完全不进入房间，也不能确认误触发率或端到端延迟。SQLite 房间持久映射到独立 Janus 数字房间，MCP 创建房间和接受邀请会驱动在线设备加入，媒体资源在会话过期时释放。Janus 协议和路由已通过内存 fake peer 测试，真实 Janus 容器及双设备网络联调仍待执行。

## 当前验证顺序

1. 用本地 Compose smoke test 验证服务启动、设备鉴权和短时断线重连；用双设备 E2E 测试覆盖配对确认、建房、在线邀请和成员查询。
2. 拉取真实 Janus 镜像，在双 Linux 模拟设备间验证 WebRTC 房间混音、无自回声和资源清理。
3. 运行模型准备脚本配置“灵矽灵矽”，使用标注样本验证误触发、漏触发、路由边界与新增缓存延迟。
4. 在 ESP32-S3 开发板验证 BluFi、I2S 采集/播放和服务端 WebSocket，并记录板型、Codec、PSRAM、内存余量和端到端延迟。
5. 用真实灵矽账号及手机端验证虚拟设备接入、BluFi 兼容性和语音工具调用。

各阶段记录实测板型、PSRAM、内存余量、音频参数和日志，稳定后再固化硬件选型。
