# 项目架构

## 组件边界

- ESP32-S3 采集和播放音频，通过认证 WebSocket 将音频帧交给 Go 后端；唤醒检测和音频分流由服务端负责。
- 灵矽提供语音识别、智能体语义理解、MCP 工具调用和语音回复。
- Go 后端维护好友、配对口令、房间、邀请确认和在线状态。
- Janus Gateway AudioBridge 在服务端处理 WebRTC 实时音频和房间混音。

## 麦克风音频路由

Go 服务为每台设备维护短时音频缓冲和路由状态：普通语音进入 Janus 房间，检测到唤醒词后清除回看缓存及房间下行，再把后续指令音频交给该设备独立的灵矽会话。灵矽 TTS 播放期间不向扬声器发送房间混音，TTS 停止后恢复房间模式。

当前代码已包含路由状态机和可替换的 `WakeWordDetector` 接口，但默认使用禁用检测器；在选定并集成实际唤醒词模型前，唤醒后控制路径不会被真实触发。Janus WebRTC/AudioBridge 端点已实现并经过内存 fake peer 测试，但 SQLite 房间尚未映射为独立 Janus 房间，创建房间或接受邀请也尚未驱动媒体会话加入。因此目前不能视为已完成端到端语音对讲。

## 首个验证顺序

1. 完成动态 Janus 房间创建及设备加入/离开生命周期。
2. 选定并集成服务端唤醒词模型，使用标注样本验证误触发和漏触发。
3. 将 MCP 的创建房间、接受邀请操作接入媒体会话，并完成双设备本地联调。
4. 在 ESP32-S3 开发板验证 BluFi、I2S 采集/播放和服务端 WebSocket。
5. 用真实灵矽账号及手机端验证虚拟设备接入、BluFi 兼容性和语音工具调用。

各阶段记录实测板型、PSRAM、内存余量、音频参数和日志，稳定后再固化硬件选型。
